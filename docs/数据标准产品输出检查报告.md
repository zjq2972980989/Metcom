# MetCom 数据标准产品输出检查报告

检查日期：2026-11-22  
检查范围：`web/frontend/src/views/StandardProducts.vue`、`web/backend/routers/products.py`、`web/backend/services/product_service.py`、`web/backend/product/paths.py`、`web/backend/metcom_product/*`、演示产品仓库及真实 ERA5 样例。

## 1. 当前实际输出逻辑

```text
StandardProducts.vue
  -> GET /api/products/sources、GET /api/products
  -> 选择 source / region / resolution / date
  -> GET /api/products/{source}/{region}/{resolution}/{date}
  -> 选择 hour
  -> GET /api/products/{source}/{region}/{resolution}/{date}/{hour}/data
  -> 预览 Header 与数据
  -> 单时次下载：
     GET /api/products/{source}/{region}/{resolution}/{date}/{hour}/download
  -> 日期级 ZIP 下载：
     GET /api/products/{source}/{region}/{resolution}/{date}/archive
```

Web 层不执行反演计算。产品由 `metcom_product.publish` / `convert_one_txt` 从已有 METCOM 结果 TXT 生成，Web 只读取 `index.json`、产品文件并下载。

单时次文件命名：

```text
MetCom_<source>_<region>_<resolution>_<YYYYMMDD>.H<HH>
```

仓库目录：

```text
<source>/<region>/<resolution>/<YYYY>/<YYYYDDD>/MetCom_*.H<HH>
```

日期级 ZIP 文件名：

```text
MetCom_<source>_<region>_<resolution>_<YYYYMMDD>.zip
```

ZIP 内沿用仓库相对目录，不重命名、不改写、不追加其他数据文件。

## 2. 是否存在独立定义的数据格式

存在一个由交付包已定义的命名文本格式：`MetCom Standard Product v1.0`。

判断依据：

- 文件使用自定义标识 `.H00` 至 `.H23`，而不是原始 `ztd_YYYYMMDDHH_sit_<source>.txt`。
- 固定 14 行 Header，含 Version、Product_Type、Source、Region、Resolution、Epoch、Time_System、经纬范围、Parameters、Units 和列顺序。
- 固定数据列：`latitude longitude PWV WVD Tm ZTD ZHD ZWD`。
- 固定参数单位和顺序：`PWV[m] WVD[g/m^3] Tm[K] ZTD[m] ZHD[m] ZWD[m]`。
- 使用 UTF-8 文本，文件由 Header 加空格分隔数据区组成。
- 使用 `index.json` 记录仓库版本、数据源和按日期聚合的时次/文件清单。
- 使用固定的 `<source>/<region>/<resolution>/<year>/<day-of-year>/` 目录规则。

因此，它不是单纯的“把原文件换个名字”，而是对原始计算结果的既有标准化文本整理。但它仍然是以普通 TXT 为基础的可读文本产品，不是新的二进制科学数据容器，也没有必要再另行设计第二种格式。

本次修改没有新增产品数据格式，也没有改变字段、单位、参数顺序或数值精度。ZIP 只是传输和归档容器。

## 3. 检查中发现并修正的问题

### 3.1 下载目录缺少整批 ZIP

修改前 Web 只支持单时次文件下载，无法一次取回一个产品日期的全部时次。已新增日期级 ZIP 接口，并保留仓库原相对路径。

### 3.2 转换 Header 分辨率被硬编码

`converter.py` 曾经始终把 Header 分辨率写成 `0.125 x 0.125 degree`，即使调用方传入 `1x1`。已改为根据产品分辨率标识解析 Header 间距，文件名仍沿用既有 `resolution` 标识。

### 3.3 原始 TXT 畸形行被静默跳过

`load_metcom_txt` 曾在列数不匹配时直接跳过该行，导致“转换成功但少数据”。现在列数异常会明确报错，避免静默丢行。

### 3.4 索引重建遇到非法文件名会中断

`rebuild_index` 现在跳过并报告无法解析的文件名，继续扫描其余合法产品，符合索引“只收录真实可解析产品”的约定。

### 3.5 前端未预览时下载文件名分支无效

已把回退文件名改为按产品命名规则动态生成，避免未读预览时下载名称不可用。

## 4. 实际格式一致性验证

使用仓库内真实样例：

```text
benchmarks/output_ERA5/2024001/ztd_20240101HH_sit_era5.txt
```

完成了 24 个时次的真实转换和打包验证：

- 转换文件数：24。
- 每个文件数据行数：1443，与对应原始 TXT 数据行数一致。
- Header：14 行，字段与既有格式一致。
- 编码：逐文件按 UTF-8 解码成功；内容为 ASCII 兼容文本。
- 参数顺序：`PWV WVD Tm ZTD ZHD ZWD`。
- 数值：经纬度按既有 3 位小数保存，参数按既有 6 位小数保存；与原始值在既定量化误差内一致。
- ZIP：24 个条目，`testzip()` 通过，条目顺序为 H00 至 H23。
- ZIP 大小：907,973 bytes。
- ZIP SHA-256：`ADAEEFC6B3B4F1DC82CADA9738C801E2D0E5A11231F3C92820DA5574E83D1A84`。

## 5. 最终方案

采用“沿用既有标准产品文本格式，只增加 ZIP 归档下载”的方案。

原因：

- 已有 `metcom_product` 已经定义并实际生成标准产品文本格式，重复设计会造成两套格式。
- 当前需求的核心是统一整理、保留命名和目录、支持一次下载，不需要改变科学数据表达。
- 单时次文件继续可读、可预览、可直接下载；日期级 ZIP 在相同内容上增加批量交付能力。
- 不触碰 ERA5、MERRA-2、CRA40、CRA V1.5、CMA-MESO 的反演计算链路。

## 6. 样例交付物

```text
deliverables/
├── MetCom_ERA5_BTH_0p125_20240101.zip
└── standard_product_ERA5_BTH_0p125_20240101/
    ├── index.json
    └── ERA5/BTH/0p125/2024/2024001/
        └── MetCom_ERA5_BTH_0p125_20240101.H00 ... H23
```

ZIP 内部结构：

```text
ERA5/BTH/0p125/2024/2024001/MetCom_ERA5_BTH_0p125_20240101.H00
...
ERA5/BTH/0p125/2024/2024001/MetCom_ERA5_BTH_0p125_20240101.H23
```

## 7. 剩余风险

- 当前格式的编码规则由实现约定为 UTF-8，Header 中没有显式 `Encoding` 字段。由于现有字符集为 ASCII 兼容，暂不修改 Header，避免破坏 v1.0 兼容性。
- 当前格式主要依赖代码与 README 说明，没有独立的形式化 JSON Schema 或交换规范文档。若后续需要跨系统长期交换，再单独制定规范，不应在本次导出改动中临时扩展格式。
